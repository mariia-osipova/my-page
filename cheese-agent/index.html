Cheese Agent: A FastAPI RAG Chatbot with Vector Search

Mariia Osipova January 20, 2025

This post is about my experience building Cheese Agent, a cheese-themed RAG chatbot project with a FastAPI backend, OpenAI embeddings, AstraDB vector search, and a vanilla JS frontend. It is deployed at cheese-agent.ai.studio. I wanted it to feel playful on the surface, but underneath it is really a small retrieval system with a clear data pipeline and a few moving parts that had to work together.

Where the idea came from

The idea for this project came to me during my first semester at university. I wanted to build something playful: an interface people would actually enjoy using, paired with a backend architecture that would teach me something along the way. It felt like the perfect balance between learning and doing something delightfully cheesy.

I knew I wanted to use a small dataset for a RAG chatbot, and while looking for random datasets online, I happened to come across the TidyTuesday repository, which collects free datasets on GitHub. That is where the idea of using cheese data came from. It was simply the first dataset I found funny enough to build a project around.

Despite its playful concept, Cheese Agent still presented some serious technical questions: how to structure the source data, generate embeddings, retrieve the right chunks, and keep the model grounded in the retrieved context. It was also a useful way to get hands-on experience with agentic workflows and retrieval-oriented tooling.

How it works

At a high level, the backend exposes a single chat endpoint in FastAPI. When a user sends a question, the backend embeds that query with OpenAI, uses the resulting vector to search the AstraDB collection, and then passes the retrieved cheese knowledge into a generation step. In other words, it follows a retrieval-augmented generation, or RAG, pattern: the chatbot does not answer from nowhere; it answers from the retrieved context that the pipeline assembles for it.

The data side matters a lot here. I used CSV-based source files and a separate ingestion script to load that material into the database ahead of time. That made the project more concrete, because I had to think not just about prompts, but also about how records are shaped, what gets embedded, and how retrieval quality depends on those choices.

What I focused on in the implementation

One part I liked a lot was the split between the backend and the frontend. The frontend stays deliberately simple: plain HTML, CSS, and JavaScript, no framework, no build step. That let me spend more attention on the backend logic instead of fighting a heavy UI toolchain. On the other side, the FastAPI service had a very clear responsibility: receive a message, run retrieval, call the model, and return an answer.

The vector database was probably the most educational part. Using AstraDB made the project feel closer to a production architecture than a notebook demo. I had to manage the collection, the embedding model choice, the ingestion process, and the relationship between retrieval and the final answer quality. Small decisions there had visible effects on how grounded the responses felt.

I also added some deliberately non-serious features around the core chat flow, like slash commands, trivia, and image interactions. I liked that contrast. The project has a playful outer layer, but underneath it there is still a retrieval pipeline, an API boundary, environment configuration, deployment setup, and data loading scripts that all have to behave correctly.

If you want to try it, the deployed app is here: cheese-agent.ai.studio. The code is here: github.com/mariia-osipova/cheese-agent.

What seems promising so far

What feels most promising to me is that this kind of project forces several useful skills to meet in one place. It is not only about prompting. It is about data preparation, embeddings, retrieval, API design, frontend integration, and deployment. That makes it a better learning project than a toy chatbot that only wraps one model call.

It also made some limitations very obvious. Retrieval quality depends heavily on the dataset and on how the source text is chunked and stored. The model can still sound confident even when the retrieved context is weak. So a lot of the real work is in building a better pipeline around the model rather than assuming the model alone is enough.

Closing thoughts

For me, Cheese Agent ended up being a good technical project because it sits between experimentation and engineering. It gave me a chance to work with ideas connected to Langflow-style agent systems and retrieval pipelines, but also to build the concrete infrastructure around them: API routes, database integration, ingestion scripts, environment variables, and a frontend that could actually present the result.

That is probably what I value most in it. It is not just a themed chatbot; it is a compact full-stack AI project where the model, the database, the data pipeline, and the user interface all have to line up. If you want to explore it, the live project is here: Cheese Agent deployed app, and the code is here: Cheese Agent on GitHub.
